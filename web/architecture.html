EduEvidence · 架构导读

一个问题进来，一份能核对的结论出去，中间发生了什么

EduEvidence 是一套开源的"决策级证据合成"流程：你把一个"要不要采用、怎么采用"的问题交给它， 它去读真实文献、主动找反证、审研究质量，最后给出可以推广 / 先试点 / 不采用 / 证据不足四选一的判定， 并附上试点方案与评价方案。它面向教育与政策等应用社科场景，也适用于企业管理、公共服务等同类决策。 这一页讲清四件事：九步流程怎么走、八个角色各管什么、结论存在哪、什么算事实、用什么跑。 本文所有说法都能在仓库里对应的文件核到（流程定义 engine/workflows.py，角色 skill/roles/registry.yaml， 产物在运行工作区 run workspace，示例 examples/ai-coding-assistant-evidence/）；文字版全文见 docs/architecture.md。

1. 一句话架构：一条带闸门的流水线

它不是"会聊天的证据助手"，而是一条每一步都要过检查的流水线：每一步有自己的输入、产物和校验门， 产物一旦落盘就是事实、只增不改，报告只是这些事实的投影（可以删掉重建，改了报告也改不了结论）。 "跳过验证直接给结论"这条路在结构上就走不通。

框定 → 检索 → 抽取 → 质询 → 审计 → 裁决              （Research Core 前 6 步 · 证据纪律）
    → 适用性 → 干预设计 → 评价方案                    （Decision Extension 后 3 步 · 证据到行动）

Projection 投影（报告 / 导出）在科学流程之外：渲染失败只影响产物，不影响任何结论。

说人话的版本：先把问题框清楚 → 去读真实文献（读全文，不看摘要）→ 把每条发现抽出来 → 专门去找反证 → 审这些研究做得够不够好 → 下判定 → 说清适用边界 → 设计一个最小试点 → 写清怎么验收。前六步管"证据站不站得住"，后三步把证据变成可执行的行动。

2. 每一步留下什么文件

流程说"做什么"，能力（capability，即"用什么本事做"）说"靠什么动作完成"，产物说"做完了留在磁盘上的东西"。 这条对应关系是写死的：能力在 engine/capabilities.py 注册、输入输出契约固定， 每一步的产物文件名固定在 scripts/orchestrator.py::STAGE_SPEC。

另外三条硬规则，让"结论可查"不是一句口号：① 能力注册项自带输入/输出契约（少一个字段就过不了门）； ② 产物文件名固定（下一步只认这个名字）；③ 每个产物要过自己的校验门（下表的右列）。 所以"这一步做没做"不靠人嘴说，看文件在不在、合不合法即可。

右列那几句"门"是什么意思，展开说：
摘要不算证据——搜索给出的摘要只能当线索，必须把正文抓回来才能进证据；
要绑原文、分清测的是什么——每条证据都要绑定可回查的原文位置，并标明它测的是哪一种结果（做题速度、考试成绩、长期保持、还是迁移）；
"做题快"≠"学会了"——系统内置护栏，禁止把任务表现当作学习效果（仓库里的说法是 task_vs_learning_guard）；
11 项定稿前检查——判定定稿前的机器检查（Pre-Verdict Gate，见 §5）。
完整方法与判据见 references/methodology-audit.md、references/tribunal-policy.md。

3. 八个角色：谁负责说"不"

角色是责任单元，不是"必须真的开出 8 个 Agent"。任务量分级（S/M/L）决定是一个模型依次扮演全部角色， 还是多个模型分工——但三条独立性约束不可协商：找反证的人必须换一个模型家族、审方法的人不看结论、 写进证据图的只能有一个人。这三条是"结论不自己给自己背书"的技术保证。

  • skeptic（找反证的人）必须来自不同模型家族：同一个模型换个会话，会沿用同一套宽容标准，等于没有独立审核。
  • method-reviewer（审方法的人）与内容判断分离：只审"怎么测的"，输入里不含结论评价，避免为结论辩护。
  • 写入者唯一：证据图的版本只能由指定的写入者提交，并行的工人不能直接写图。

八个角色依次是：research-planner（把问题框清楚：人群、干预、对照、要看的结果）、 evidence-retriever（找来源并保住出处，摘要不算证据）、 evidence-analyst（把发现抽成结构化条目）、skeptic（独立去找反证）、 method-reviewer（审研究质量与测量效度）、evidence-judge（在证据边界内下判定、划适用边界）、 intervention-designer（设计有证据支撑的试点与叫停条件）、evaluation-designer（设计能算得出的验收方案）。 角色分工写在 skill/roles/registry.yaml，提示词在 skill/agents/； 跨模型复核只在执行层真的开了多个模型时才发生，没有独立模型就如实降级为自审并标注——绝不假装做过独立复核。

4. 结论存在哪：事实 / 一次运行 / 投影

Project（一个研究问题一个项目）
  └── Evidence Graph（append-only revision）        ← 事实层（唯一真相源）
      Source → Study → Finding → EvidenceLink → Claim → Outcome → Decision
  └── Run（一次执行）
      frame.json · sources.jsonl · fetch/ · evidence.jsonl · skeptic.json
      methodology.json · raw_verdict.json · final_verdict.json · applicability.json
      intervention.json · evaluation.json · state.json · trace.jsonl
      检索审计：search-provenance / attempts / screening / exclusion（+ Sciverse chunks.jsonl）
  └── DecisionSnapshot（每次裁决的不可变快照）
  └── Projections（可删可重建）
      result.json / result.zh.json / HTML 报告 / 图表 / 导出包
三条边界，值得记一下：① 事实只存在证据图里，不在报告里——报告坏了、重渲染了，结论不会变； ② 投影（Projection）不属于科学流程，它不在九步之内，渲染失败只影响发布，不影响任何判定； ③ 检索留痕本身就是证据链的一部分——没有出处记录的检索结果只是"候选"，不能算证据。 Sciverse 通道拿到的段落定位就按第 ③ 条写进 chunks.jsonl，并标注 discovery_only_requires_content_fetch（意思是：这只是定位，必须再读回正文）。

三层的差别，用一句话说清：Project 是长期研究项目（一个问题对应一个项目，能跨学期一直用）； Run 是一次执行（这一轮跑到哪、留下哪些文件）；Projection 是投影（给人看的报告、图表、导出包）。 事实层只有一份：证据图。图上每次提交都生成一个完整的新版本（rev-N）并原子切换指针，旧版本只增不改； 每次裁决另外留下一个不可变的决定快照，报告落款绑定的是具体哪个版本——所以"引用的是哪一版证据"永远查得到。

5. 定稿前的机器检查：Pre-Verdict Gate

判定不是模型写完就算数。定稿前有一道确定性检查（不调模型、不联网，只读这次运行的产物），共 11 项， 每项给 pass / warn / fail 三种结论：

检查项不通过会怎样
研究框架合法问题没框清楚，后面全部无效
来源非空且合法没有可用来源，不能往下走
证据非空且合法抽不出结构化证据，不能裁决
来源已去重同一篇论文的镜像 URL 会重复计数，必须先合并
反证检索确实做过没有真正找过反证，不许下结论
方法学审计有效审计缺失、判 FAIL，或把"任务表现"等同于"学习"，都会挡住
主张与证据对得上引用的证据必须真实存在，且不能和自己主张的方向相反
结果映射完整结论用到的结果类型必须是登记过的，框架里声明要查的不能漏
结论边界写清楚必须写明"能主张什么、不能主张什么、哪里超出了证据"
独立研究计数独立研究/样本要数清楚；只有 1 项独立研究时不允许给 High
置信度可复算最终置信度必须是公式算出来的，并保留模型原值以便对比

关键项失败会封顶：不允许高置信度，也不允许直接给"可以推广"，只能降到"先试点"或"证据不足"。 结果写在运行目录的 gate_report.json 里，可复核。

6. 执行层：两种跑法，和一道审批闸门

维度Mode A · Platform NativeMode B · Agent MCP Enhanced
依赖无（提示词 + 标准库脚本）daemon / CLI / MCP Server
检索内建通道（含 Sciverse 等 key 通道）同上 + 多 CLI 派遣
模型单模型按角色分工的多模型
失败语义直接降级超时/失败降级回 Mode A 语义
detect_agent_mcp()            → 扫描可用 CLI 与模型（无预设默认值）
build_recommendation_table()  → 按 ROLE_REQUIREMENTS 生成"角色 → 模型"候选表
用户确认                       → write_approval()：写入 approval.json（含角色映射哈希）
safe_spawn(role)              → 未确认 / 哈希不匹配 / CLI 越权 ⇒ AGENT_MCP_APPROVAL_REQUIRED（不 spawn）
cross_model_review()          → 独立模型复核草稿裁决；无独立模型时降级为原生自审并标注

要点 两种跑法只影响"谁来执行"，不影响科学标准：Mode A 没有任何外部依赖， 用提示词加标准库脚本就能跑完九步；Mode B 才接入外部 CLI / 多模型，失败时照样降级回 Mode A（并如实标注）。 模型清单来自真实扫描，角色提示词里不写模型名——一旦允许"悄悄换模型"，skeptic 的跨家族独立性就名存实亡， 而报告读起来毫无差别；审批哈希（agent_mcp_approval.json）把"用户同意的是哪套映射"钉死， 未经确认的派遣一律返回 AGENT_MCP_APPROVAL_REQUIRED 且不启动。

7. 跟着一条真实证据链走一遍

抽象流程读十遍，不如跟一条真的走一遍。这里用仓库里两个真实产物包，把九步落到具体文件上。 先说最值得记住的一课：下面这个例子中，"练习时做题变快"和"撤掉 AI 后还能不能自己做"是两回事， 而这正是判定从"可以推广"降到"先试点"的原因。

这一步做什么留下什么文件这一份里到底是什么
框定问题frame.json问题、人群、对照、要看的结果写清楚；本例是"大一 C 语言课该不该放开生成式 AI 编程助手"
检索文献sources.jsonl + fetch/8 篇来源（7 篇带 DOI 的期刊/会议论文 + 1 篇预印本），正文抓到本地，另附检索审计四件套
抽取证据evidence.jsonl12 条证据，每条绑定原文位置；把"任务表现"和"学习效果"分开记，不混为一谈
反向质疑skeptic.json9 项反证检查逐条给结论；本例最有力的反证是：撤掉 AI 后独立考试 −17%（950 人）
方法学审计methodology.json15 项审计；明确写下"练习涨 48–127% 与独立考试 −17% 同时存在，不能等同"
下判定final_verdict.jsonPILOT（先试点）；把握程度 Moderate，分数按公式算出可复算
报告reports-5themes/*.html五种版式的双语报告（中英各一份结果文件），里面的数字由提取器从结果文件读出，不是手写的
四种判定什么时候给
ADOPT · 可以推广关键结果有较强的直接证据、风险可控、且场景对得上。教育场景还要求直接测到"学习/保持/迁移"——只测出"做题变快"不给
PILOT · 先小范围试点方向有积极证据，但长期效果、迁移或风险还不清楚；先在有界范围内试，用统一的延迟测评验收
REJECT · 不采用关键结果稳定为负，或风险明显大于收益；此时不输出试点方案
INSUFFICIENT EVIDENCE · 证据不足来源太少、太间接、研究设计太弱，或分歧无法解释；写明"什么证据会改变这个判断"

四态之上还有一条机器规则：判定由公式与门决定，不是模型自由发挥—— 只要存在"反对采用"的独立证据，结果就会走到 REJECT；把握程度为 Low 或 Insufficient 时永远不可能给 ADOPT。

另一个例子是 examples/spaced-retrieval-practice/（间隔重复与检索练习能否替代集中式复习）。 它的特别之处在于：7 篇来源全部走 Sciverse 通道——先用语义检索定位段落，再按定位把正文读回来核验，全部带 DOI； 6 条证据聚成 3 条主张（延迟保持、收益大小取决于设计、迁移也受益）；结论同样是 PILOT， 理由是"延迟保持的证据一致，但直接来自程序设计课堂的现场证据偏少"。它给出的试点很具体： 第 1 周统一前测 → 第 2–13 周每周 10 分钟闭卷检索练习 → 第 14–16 周无辅助延迟测试与新题型迁移任务； 只要延迟测试低于基线、或完成率掉到 60% 以下，就叫停。 两个例子都说明同一件事：判定偏保守，不是不敢下结论，而是证据只支持到这里。

两个例子的诚实标注：主例的文献是人工整理（data_origin=manual_curated）， 它演示的是"一份完成的评审长什么样"，不代表已经跑过模型研究运行； 第二例的检索是真实联网的（data_origin=real_run_sciverse），但结论针对的是演示问题，不等于任何真实学校的现场结论。

eduevidence run --question "大一 C 语言课程是否应该允许学生使用生成式 AI 编程助手？" --run-id ai-cs1
eduevidence status --run-id ai-cs1     # 阶段状态与待补产物
eduevidence gate   --run-id ai-cs1     # Pre-Verdict Gate
eduevidence report --run-id ai-cs1 --theme claude

8. 这套说明凭什么不跑偏

同一套约定会同时出现在好几个地方：流程注册表、能力注册表、角色注册表、角色提示词、每一步的任务简报、 子技能配方、工作流手册、打包清单。只要有一处改漏，"可追溯"就变成口号。所以这里不靠人工校对，靠机器对账：

python scripts/skill_lint.py                  # 结构：文件在不在、frontmatter 对不对
python scripts/check_protocol_alignment.py    # 语义：五方说的是不是同一件事
python scripts/check_version_consistency.py   # 版本：单一权威
python scripts/generate_metrics.py --check    # 数字：文档与仓库一致
对齐门是真的会抓到问题的——在本版本开发中它抓出过 4 个不存在的能力 ID、1 份落后两个大版本的打包清单、 以及 2 处过期的测试计数。新增一项能力 / 子技能 / 角色 / 检索通道的步骤见 CONTRIBUTING.md。
